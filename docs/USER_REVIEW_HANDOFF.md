## 1. 지금 무엇을 확인하는 작업인가요?

질문은 하나입니다. **“이 제품의 공식 원재료와 기능성 원문으로, 검토 대상 원료의 기능성 역할을 확인할 수 있는가?”**

이 작업은 제품을 먹으면 효과가 있는지, 안전한지, 광고가 적법한지를 판단하는 작업이 아닙니다.
현재 보존된 C003 스냅샷과 그 검토팩에 연결된 규칙을 대조합니다. 오늘 판매 중인 제품의
현물·배합·광고까지 확인한 것으로 확대하지 않습니다.

이미 끝난 검토와 이번 검토는 다음처럼 구분합니다.

| 검토 | 확인한 대상 | 현재 상태 |
|---|---|---|
| 제품 매핑·원문 검토 v2 | 제품과 원료군의 매핑, 기능성 원문을 검토에 쓸 수 있는지 | 100행 완료; 매핑 99건 일치·1건 오류 |
| 원료 규칙 검토 | 공식 원료형·기능 문구와 규칙의 대조 | CHOI 추출·DOHA 검토 기록 있음 |
| **이번 제품별 역할 검토 A** | 각 제품에서 대상 원료와 기능성의 연결 근거 | **전체 275행 중 274행 대기** |

유효한 1행은 v2 매핑 오류를 이어받아 제외한 행입니다. 새 제품별 사람 검토 1건이 완료됐다는 뜻은 아닙니다.
CHOI·DOHA의 기존 규칙 확인 기록을 새 제품별 판정으로 복사하지 않습니다.

## 3. 판정 기준

| 보내실 판정 | 선택할 때 | 피해야 할 판단 |
|---|---|---|
| 기능성 확인 | 원재료의 대상 원료형과 해당 기능성 원문 사이의 연결을 규칙에 따라 확인할 수 있음 | 제품명만 보고 확인, 다른 원료의 기능성을 대상 원료에 연결 |
| 비기능성 확인 | 대상 원료가 비기능성 역할로 들어갔다는 명시적 근거가 있음 | 기능성 문구가 없다는 이유만으로 비기능성이라 확정 |
| 불확실 | 연결 근거 부족, 복합원료 간 귀속 모호, 전문가 해석 필요, 자료 충돌 | 통과율을 높이기 위해 기능성 확인으로 바꾸기 |

- 원재료 근거와 기능성 근거는 각각 원문에서 복사합니다. **관련 구절을 찾지 못했다면 “없음”**이라고 적고, 왜 판단이 어려운지 설명합니다.
- `불확실`도 정식 검토 결과입니다. 다만 아직 읽지 않은 상태는 `불확실`이 아니라 **미검토**입니다. 미검토 제품은 양식을 비워둡니다.
- 전문가 판단이 필요한지는 사용자님이 억지로 해결할 필요가 없습니다. “불확실 / 전문가 해석 필요: …”로 남겨주세요.
- 다른 사람이 함께 확인했다면 각자의 실제 결과를 구분합니다. 의견이 다르면 다수결이나 AI 판단으로 덮지 않고 이견을 보존합니다.
- CHOI·DOHA는 검토자 식별자입니다. 약사·영양사 자격을 뜻하지 않으며, 이번 대조를 전문가의 임상 검토로 표시하지 않습니다.

## 4. 채팅 답변 양식

다음은 **한 제품용 빈 양식**입니다. 다섯 제품의 신고번호가 들어간 양식은 위 답변 파일에 있습니다.

```text
검토 배치: batch-001
실제 검토자: [직접 검토한 사람의 식별자]

원료군: milk_thistle
신고번호: [검토지의 신고번호]
판정: [기능성 확인 / 비기능성 확인 / 불확실 중 실제 판단]
원재료 근거: [원문 구절 그대로 / 관련 구절 없음]
기능성 근거: [원문 구절 그대로 / 관련 구절 없음]
판단 이유: [왜 연결됨·비기능성·불확실이라고 판단했는지]

검토 완료 시각: [실제 날짜·시각·시간대]
```

검토 후 지금 최종 확인하는 경우에는 시각 대신 **“위 결과를 현재 시각에 최종 확인함”**이라고
직접 보내셔도 됩니다. 이 명시적 확인이 있을 때만 에이전트가 확인 시점의 시각을 기록합니다.
여러 날짜에 나눠 검토했고 함께 재확인하지 않았다면 제품별 시각을 따로 알려주세요.
과거 확인을 지금 한 것으로 바꾸거나 미래 시각·추정 시각을 넣지 않습니다.

“다 했음”, “전부 일치”, “승인”만으로는 어떤 제품을 어떤 근거로 판정했는지 알 수 없습니다.
제품별 결과가 있어야 라벨로 반영할 수 있습니다. 반대로 아직 헷갈리면 **신고번호와 질문만**
보내셔도 됩니다. 그 질문을 완료 판정으로 기록하지 않습니다.

## 5. 사용자와 에이전트의 담당 범위

| 담당 | 할 일 | 완료 확인 |

| 에이전트 | 확인된 행만 로컬 CSV 형식으로 반영, 묶인 규칙 버전 적용, 검증 실행 | 실제 `PENDING`/`INVALID`/`COMPLETE`와 종료코드 보고 |

| 에이전트 + 필요 시 사용자 | 공식 출처 최신성 재확인, 변경 시 재검토 범위·새 버전 계획 제시 | 실제 재확인 증거 확보; 기존 pack 보존 |

인용문·검토자·날짜를 만들어 넣지 않습니다. 확인된 답변을 형식화하는 것과 판정을 생성하는 것은 다릅니다.

## 7. 보내주신 다음의 처리와 완료 조건

1. 에이전트가 원문·식별자·입력 이력을 대조합니다. 해석이나 실제 검토 의사가 불분명하면 먼저 질문합니다.
2. 내용이 확인된 행만 반영한 뒤 **매 배치 실제 검증기**를 실행합니다. 불완전한 초안은 라벨 CSV에 부분 저장하지 않습니다.
3. 결과가 `PENDING`이면 남은 행 수를 알려드리고 다음 미검토 배치를 준비합니다.
4. `INVALID`이면 구체적인 무결성·입력·최신성 문제를 해결합니다. 기존 라벨 일괄 초기화나 날짜 조작으로 통과시키지 않습니다.
5. 모든 라벨이 유효하여 `COMPLETE`일 때만 원문·검토자 정보가 빠진 공식 집계 파일을 만듭니다.

**모든 행을 검토하는 것과 모든 원료가 적격인 것은 다릅니다.**
`불확실` 또는 기계의 잘못된 확인이 있으면 검토팩은 완료돼도 해당 원료는 `ROLE_INSUFFICIENT`일 수 있습니다.
지표를 좋게 만들기 위해 사람 답을 기계 판정에 맞추지 않습니다. 코드 테스트 커버리지도 판정 정확도가 아닙니다.

A가 완료되어도 광고 근거 B는 `NOT_MEASURED`, 확장 추천 C는 `BLOCKED`, `finalized=false`를 유지합니다.
광고 검증·추천·최종 원료 선정은 별도 증거와 승인 범위가 필요합니다. 프론트엔드·개인화로 바로 넘어가지 않습니다.

## 8. 날짜와 파일 보존 주의

- 저장된 공식 최신성 확인 시각은 `2026-09-04T17:31:53+09:00`입니다. 현재 코드의 **내부 7일 최신성 기준**으로는 `2026-09-11T17:31:53+09:00`에서 7일에 도달하며, 이를 넘기면 재확인이 필요합니다.
- 이 시각은 **사용자가 검토를 서둘러 끝내야 하는 제출 마감도, 법령의 만료일도 아닙니다.** 이번 핸드오프 작성 중 공식 사이트를 다시 조회한 것은 아닙니다.
- 기한을 넘겨도 작성한 답은 보존합니다. 에이전트가 실제 공식 출처를 재확인하고, 규칙 해시 변경이 기존 pack에 미치는 영향을 확인한 뒤 재개합니다. 날짜만 고쳐 검증을 통과시키지 않습니다.
- 현재 규칙이나 표본이 바뀌면 이전 답을 새 버전에 자동 전용하지 않습니다. 새 버전·별도 pack·필요한 재검토 범위를 먼저 정리합니다.
- 사용자는 `manifest.json`, `samples.csv`, 기존 v2 라벨, 규칙 JSON, 기계 판정 열을 고치지 않습니다. 기존 pack 폴더 안에는 파일을 추가하지 않습니다.
- 검토 원문·개인별 답변은 로컬 ignored 경로에 보존합니다. Git에는 지침과 허용된 집계만 기록합니다. 키·계정·건강정보는 답변에 넣지 않습니다.
