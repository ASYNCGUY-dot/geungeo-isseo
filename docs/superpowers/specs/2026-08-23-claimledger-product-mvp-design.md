# 근거있어 제품 중심 MVP 설계 — ClaimLedger 엔진

- 작성일: 2026-08-23
- 상태: 사용자 대화 승인 후 문서 검토 대기
- 선행 게이트: Phase 0 C003 데이터 신뢰 게이트 `CONTINUE_PRODUCT_MVP`
- 대상 브랜치: `phase-0-c003-data-gate`

## 1. 목적

근거있어는 건강기능식품 광고의 개별 주장을 공식 제품정보와 과학적 근거에 대조하여,
무엇을 확인했고 무엇을 확인하지 못했는지 출처와 함께 근거영수증으로 보여주는
서비스다. ClaimLedger는 이 판정 경계를 구현하는 내부 검증엔진이다.

최우선 목표는 사용자가 빠르게 많은 판정을 받는 것이 아니라, 불확실한 입력이 근거 있는 긍정 판정으로 잘못 노출되는 일을 막는 것이다. 절대적 정확도를 약속하지 않으며, 제품 신원·광고 원문·근거 적용 가능성을 확인할 수 없으면 보수적으로 중단한다.

## 2. 비협상 원칙

1. 제품의 공식 신고번호를 정본 식별자로 사용한다.
2. 제품명과 업체명 검색은 후보 제시에만 사용한다.
3. 사용자가 제품을 확정하기 전에는 제품 수준 판정을 내리지 않는다.
4. OCR과 LLM은 광고 문구 및 주장 후보를 만들지만, 최종 판정을 내리지 않는다.
5. 최종 판정은 버전이 지정된 결정론적 규칙 엔진만 생성한다.
6. 데이터 누락, 출처 장애, 근거 충돌은 긍정 판정으로 변환하지 않는다.
7. 광고 판정과 복용 주의 신호를 분리한다.
8. 개인 맞춤 효과·안전·복용 가능 여부는 현재 MVP에서 판단하지 않는다.
9. 모든 결과는 원문, 제품 신원, 출처, 조회 시각, 근거 스냅샷, 규칙 버전으로 재현 가능해야 한다.
10. 단일 신뢰 점수 대신 주장별 근거 영수증을 제공한다.

## 3. 범위

### 3.1 핵심 원료군

- 루테인·지아잔틴
- 오메가3
- 프로바이오틱스

### 3.2 확장 원료군 선정

다음 비교군을 유지한다.

- 밀크씨슬
- 비타민 D
- 홍삼
- 코엔자임 Q10
- 마그네슘

확장 원료 두 개는 다음 역할로 선정한다.

- 데이터와 규칙이 비교적 명확한 원료 한 개
- 광고 위험과 사용자 가치가 높은 원료 한 개

선정 기준은 데이터 품질, 광고 위험과 가치, 기능성 다양성, 구현 가능성을 균형 있게 적용한다. 전체 통계와 후보별 20개, 총 100개의 사람 검토 표본을 사용한다. 홍삼은 고위험·고가치 비교군으로 유지한다.

### 3.3 현재 MVP에서 제공하는 기능

- 광고 이미지 업로드
- 판매자 상품 또는 광고 페이지 URL 입력
- 이미지와 URL의 교차검증
- 광고 이미지 OCR 및 사용자 확인
- 판매자 등록 콘텐츠의 광고 주장 추출 및 사용자 확인
- 공식 제품 후보 검색 및 사용자 제품 확정
- 공식 기능성 문구 비교
- 과학 논문 RAG와 적용 가능성 분류
- 결정론적 주장별 판정
- 공식 제품 주의사항과 공식 원료 수준 병용 주의 신호
- 익명 임시 분석
- 로그인 후 영수증 저장과 버전 비교

### 3.4 현재 MVP에서 제공하지 않는 기능

- 개인 맞춤 효능 판단
- 개인별 복용 안전 또는 복용 가능 판정
- 질환 진단·치료·예방 조언
- 의약품 대체 또는 복용량 변경 지시
- 사용자 후기와 Q&A의 광고 판정
- 공식 심의 통과 또는 법적 확정 표현
- 근거가 없는 종합 상품 순위

공식 원료 수준 병용 주의 신호는 사용자가 선택한 제품에 공개된 공식 주의 문구를 출처 그대로 안내하는 기능이다. 사용자의 실제 약물 목록과 대조하거나 상호작용 유무, 복용 가능 여부, 위험도를 판단하는 기능이 아니다. 따라서 기존의 개인 맞춤 안전성과 의약품 상호작용 평가 제외 원칙을 변경하지 않는다.

## 4. 공개 판정 상태

공개 판정 상태는 다음 다섯 개로 고정한다.

| 코드 | 화면 문구 | 의미 |
|---|---|---|
| `confirmed` | 확인됨 | 제품·주장·근거가 명시적 규칙으로 일치 |
| `mismatch` | 근거 불일치 | 광고 표현과 공식 인정 범위 또는 조건이 불일치 |
| `insufficient` | 근거 부족 | 관련 자료는 있으나 주장을 확인하기에 부족 |
| `unverifiable` | 검증 불가 | 제품 신원, 필수 데이터, 출처 또는 규칙이 부족 |
| `contradicted` | 직접 반박됨 | 직접 적용 가능한 신뢰 근거가 주장을 명확히 반박 |

`confirmed`는 해당 광고 주장이 확인된 근거 범위와 일치한다는 뜻이다. 개인에게 효과가 있거나 안전하다는 의미가 아니다.

## 5. 아키텍처

시스템은 다음 경계로 분리한다.

| 영역 | 책임 | 최종 판정 권한 |
|---|---|---:|
| React 웹 | 입력, 사용자 확인, 결과 표시 | 없음 |
| FastAPI | 워크플로, 인증, 권한, 요청 계약 | 없음 |
| 분석 파이프라인 | URL 수집, OCR, 주장 추출, 근거 검색 | 없음 |
| 결정론적 엔진 | 버전 규칙으로 주장별 판정 | 있음 |
| 감사 저장소 | 원문, 변경, 출처, 규칙과 결과 보존 | 없음 |

React나 FastAPI 라우터에 판정 규칙을 중복 구현하지 않는다. 외부 모델 및 데이터 공급자는 포트 뒤에 두어 테스트에서 재현 가능한 대체 구현을 주입할 수 있게 한다.

## 6. 핵심 데이터 모델

### 6.1 제품과 공식 정보

- `ProductRecord`: 신고번호, 제품명, 업체명, 공식 기능성, 원재료, 섭취방법, 원본 출처, 조회 시각
- `ProductSearchDocument`: 검색용 정규화 텍스트와 정규화 규칙 버전
- `IngredientMapping`: 원료 후보와 검증 상태
- `OfficialFunctionStatement`: 공식 기능성 문구와 규칙 기반 구조화 결과
- `OfficialProductCaution`: 공식 제품 섭취 시 주의사항 원문
- `CautionSummary`: 원문과 분리된 사용자용 요약

제품 검색은 후보를 반환할 뿐 신원을 확정하지 않는다. 원료 매핑 상태는 `verified_mapping`, `ambiguous`, `unverifiable`로 구분하고, 일치 필드·일치 원문·규칙 버전을 기록한다.

### 6.2 광고 원문과 주장

- `AdvertisementSource`: 이미지 또는 URL, 콘텐츠 해시, 수집 시각
- `OCRBlock`: 원문, 신뢰도, 이미지 좌표, OCR 모델 버전, 사용자 확인값
- `AtomicClaim`: 원문 범위, 주체, 효과, 대상, 용량, 기간, 결과, 표현 강도, 확인 상태

모든 `AtomicClaim`은 원문 범위로 역추적할 수 있어야 한다. LLM이 원문에 없는 수치·대상·효과를 보완하지 않는다.

### 6.3 과학 근거

- `ScientificEvidenceCard`: 논문 식별자, 연구 유형, 대상, 원료·제품, 제형, 용량, 기간, 결과, 한계, 출처
- `EvidenceApplicability`: `DIRECT`, `PARTIAL`, `INDIRECT`, `NOT_APPLICABLE`, `UNVERIFIABLE`
- `EvidenceSnapshot`: 판정에 사용한 근거 집합과 조회 상태

근거 범위를 공식 제품, 공식 원료 기능성, 과학적 원료 근거, 과학적 완제품 근거로 구분한다. 검색 결과 0건, 검색 서비스 장애, 간접 근거만 존재하는 상황을 서로 다른 상태로 보존한다.

### 6.4 주의 신호

- `InteractionEvidence`: 공식 원료 수준 병용 주의 원문과 출처
- `MinimalSafetyContext`: 장기 저장하지 않는 최소 임시 문맥
- `SafetySignal`: 일반 주의 신호이며 `is_safety_clearance`는 항상 `false`

향후 확장을 위해 일반 주의 신호와 개인화 안전성 평가의 인터페이스를 분리한다. 현재 MVP는 일반 주의 신호만 구현한다.

## 7. 입력 방식과 URL 분석

### 7.1 지원 입력

- 이미지로 확인
- 상품·광고 링크로 확인
- 이미지와 링크를 함께 사용

이미지와 링크가 함께 제공되면 상품명, 회사명, 대표 이미지, 원료, 용량, 광고 문구, 옵션을 교차검증한다. 불일치는 사용자 확인 없이는 해소하지 않는다.

### 7.2 URL 분석 대상

다음 판매자 또는 제조사 등록 콘텐츠만 분석한다.

- 상품명
- 상품 고시정보
- 상품 설명
- 상세페이지 이미지
- 제조사·판매자가 제공한 표시정보와 원료표

다음 콘텐츠는 분석에서 제외한다.

- 사용자 후기와 별점
- 플랫폼의 AI 후기 요약
- 상품 Q&A
- 구매자 사진
- 추천 상품
- 플랫폼 자동 생성 문구
- 작성 주체를 확인할 수 없는 콘텐츠

각 영역에 `content_origin`을 기록한다.

```text
seller_product_title
seller_notice
seller_description
seller_detail_image
manufacturer_label
platform_generated
user_review
user_qna
recommended_product
unknown
```

처음 다섯 상태만 주장 추출 입력이 될 수 있다. `unknown`은 자동 포함하지 않는다.

### 7.3 URL 수집 절차

1. URL과 목적지의 안전성을 검사한다.
2. 정적 HTML, 메타태그, JSON-LD, 이미지 후보를 우선 수집한다.
3. 필요할 때만 격리된 브라우저에서 제한적으로 렌더링한다.
4. 상품 영역과 비상품 영역을 분리한다.
5. 판매자 등록 콘텐츠의 문구와 이미지를 추출한다.
6. 상세 이미지에 OCR을 수행한다.
7. 사용자에게 페이지, 상품, 분석 범위를 확인받는다.
8. 기존 주장·근거·판정 흐름으로 전달한다.

로그인, CAPTCHA, 앱 전용 페이지, 로봇 차단 또는 불명확한 상품 영역은 우회하지 않는다. 사용자에게 현재 화면 캡처를 요청하는 안전한 대체 경로를 제공한다.

### 7.4 URL 보안

URL 수집기는 FastAPI 프로세스 및 내부망과 격리한다. 다음을 차단한다.

- 비HTTP 스킴
- localhost, 사설 IP, 클라우드 메타데이터 주소
- DNS 확인 후 목적지가 바뀌는 접근
- 검증되지 않은 리디렉션
- 인증정보가 포함된 URL
- 과도한 응답, 압축 폭탄, 비정상 파일, 과도한 지연
- 페이지 콘텐츠를 시스템 명령으로 취급하는 프롬프트 인젝션

리디렉션마다 목적지를 다시 검증한다. URL 수집 결과는 검증된 사실이 아니라 페이지에서 관찰한 후보 데이터다.

### 7.5 옵션과 페이지 변경

용량, 제형, 배합, 대상이 다른 옵션을 같은 제품으로 자동 확정하지 않는다. 옵션이 모호하면 `confirmed`를 차단한다.

페이지 재수집 시 기존 스냅샷과 현재 콘텐츠를 비교한다. 광고 문구나 상품이 바뀌면 기존 영수증을 현재 페이지 결과처럼 표시하지 않고 새 분석 버전을 만든다.

## 8. OCR, 주장 추출, RAG, 판정 흐름

### 8.1 OCR

원본 이미지, 콘텐츠 해시, 블록 좌표, 신뢰도, OCR 버전을 보존한다. 낮은 신뢰도, 숫자, 단위, 부정 표현, 치료·예방 표현은 사용자 확인 없이는 판정 입력으로 사용할 수 없다.

### 8.2 LLM 주장 추출

LLM은 광고 원문을 원자적 주장으로 추출하고 정규화한다. 제품 신원, 근거 채택, 최종 판정을 결정하지 않는다. 각 주장은 원문 범위와 연결되며, 모호하거나 고위험인 주장은 사용자가 확인한다.

표현 강도는 가능성, 도움, 개선, 보장, 치료·예방의 순서로 구분한다. 더 강한 표현을 약한 표현으로 자동 완화하지 않는다.

### 8.3 과학 논문 RAG

검색은 원료·완제품, 제형, 용량, 기간, 대상, 결과를 포함한다. 연구 유형과 직접 적용 가능성을 분류한다. 논문을 찾았다는 사실만으로 광고를 확인하지 않는다.

### 8.4 결정론적 판정

판정 입력에는 확인된 제품, 확인된 주장, 공식 정보, 근거 스냅샷, 적용 가능성, 출처 상태, 규칙 버전이 포함된다.

판정은 다음 순서로 fail-closed 처리한다.

1. 제품 신원과 사용자 확인을 검사한다.
2. 광고 원문과 주장 확인 상태를 검사한다.
3. 필수 공식 데이터와 출처 상태를 검사한다.
4. 광고 표현과 공식 기능성의 범위·강도를 비교한다.
5. 과학 근거의 직접 적용 가능성과 충돌을 검사한다.
6. 고정 우선순위로 공개 판정을 생성한다.
7. 사유 코드, 한계, 규칙 버전, 근거 스냅샷을 보존한다.

`confirmed`는 모든 필수 게이트가 일치할 때만 가능하다.

## 9. 분석 상태와 확인 게이트

`AnalysisSession` 상태는 다음 흐름을 따른다.

```text
created
→ media_or_url_received
→ source_processed
→ source_confirmation_required
→ ocr_completed
→ ocr_confirmation_required
→ product_candidates_ready
→ product_confirmation_required
→ claims_extracted
→ claim_confirmation_required
→ evidence_retrieved
→ decision_completed
```

별도 상태는 `recoverable_error`, `blocked_unverifiable`, `expired`, `cancelled`다.

확인 게이트는 다음과 같다.

- G0 웹 원문과 분석 범위 확인(URL 입력 시)
- G1 제품 신원 확인
- G2 OCR 문구 확인
- G3 광고 주장 확인
- G4 결과와 한계 확인

서버만 상태를 전이하며, 사용자는 확인·수정·제외·재시도를 요청한다. 같은 요청이 반복되어도 중복 결과를 만들지 않는다.

## 10. FastAPI 계약

API는 `/api/v1`로 시작한다.

### 10.1 핵심 엔드포인트

```text

POST /api/v1/analyses/{id}/media/complete
GET  /api/v1/analyses/{id}
GET  /api/v1/analyses/{id}/source
PUT  /api/v1/analyses/{id}/source/confirmation
GET  /api/v1/analyses/{id}/ocr
PUT  /api/v1/analyses/{id}/ocr/confirmation
GET  /api/v1/products/search
GET  /api/v1/analyses/{id}/product-candidates
PUT  /api/v1/analyses/{id}/product-confirmation

PUT  /api/v1/analyses/{id}/claims/confirmation
POST /api/v1/analyses/{id}/evaluate
GET  /api/v1/analyses/{id}/receipt
```

평가 요청에는 판정값을 받지 않는다. 확인된 OCR, 제품, 주장 버전을 참조하고 서버가 현재 확정 버전인지 검증한다.

### 10.2 비동기 처리

REST로 명령을 받고 작업 큐에서 URL 수집, OCR, LLM, RAG를 실행한다. 진행 상황은 SSE로 알리고, 연결이 끊기면 상태 조회 폴링으로 복구한다. 판정 결과는 데이터베이스에 원자적으로 확정된 뒤 사용자에게 전달한다.

### 10.3 오류 계약

오류는 입력, 인증, 소유권, OCR, 제품 신원, 주장, 출처, 근거, 판정, 저장, 호출 제한, 내부 오류로 분류한다. 사용자 메시지와 내부 오류를 분리하며 다음 필드를 제공한다.

```json
{
  "error": {
    "code": "PRODUCT_IDENTITY_UNCONFIRMED",
    "message": "제품을 먼저 확인해 주세요.",
    "retryable": false,
    "user_action": "select_product",
    "analysis_id": "uuid",
    "trace_id": "uuid"
  }
}
```

외부 서비스 장애는 근거 없음으로 표현하지 않는다.

## 12. 로그인, 저장, 개인정보

분석은 익명으로 가능하고 장기 저장은 로그인을 요구한다. 익명 분석은 짧은 보존기간을 적용하고 계정에 자동 연결하지 않는다. 로그인 전 분석을 계정에 저장할 때는 별도 동의를 받는다.

MVP 기본 인프라 후보는 Supabase Auth, PostgreSQL, Storage다. FastAPI는 JWT 발급자·대상·서명·만료와 데이터 소유권을 재검증한다. 도메인 계층은 Supabase SDK에 직접 의존하지 않는다.

사용자가 저장을 선택한 경우 광고 원문 또는 해시, 확인된 OCR, 제품 신고번호, 주장, 출처, 근거 카드, 판정, 규칙 버전, 감사 이벤트를 보존할 수 있다.

질환명, 약물 목록, 임신·수유 상태, 알레르기 상세, 개인 복용량 판단은 기본적으로 장기 저장하지 않는다. 토큰, 키, 불필요한 건강정보, 사용자 후기와 프로필은 일반 로그에 기록하지 않는다.

## 13. 감사와 재평가

일반 운영 로그와 판정 재현을 위한 감사 로그를 분리한다. 감사 로그에는 사용자 확인·수정, 제품 선택, 출처와 근거 스냅샷, 적용 가능성, 규칙 실행, 결과 버전, 변경 이유를 기록한다.

과거 판정을 수정해 덮어쓰지 않는다. 규칙이나 근거가 바뀌면 새 판정 버전을 만들고, 이전과 현재의 판정·기준일·규칙 버전·변경 이유를 비교한다.

## 14. 테스트 전략

테스트는 도메인 불변 조건, 컴포넌트, 계약, 통합 파이프라인, 고정 평가 세트, 사용자 이해도, 보안·개인정보·장애 복구의 일곱 계층으로 구성한다.

### 14.1 고정 판정 평가 세트

| 판정 | 사례 수 |
|---|---:|
| `confirmed` | 20 |
| `mismatch` | 25 |
| `insufficient` | 20 |
| `unverifiable` | 25 |
| `contradicted` | 10 |
| 합계 | 100 |

원료별 구성은 핵심 세 원료 각 15건, 확장 원료 두 개 각 10건, 제품 신원·출처 장애·교차 조건 35건이다.

개발 세트와 동결 평가 세트를 분리한다. 평가세트 실패 사례를 삭제하지 않고 버전 이력과 함께 유지한다.

### 14.2 URL 평가 세트

최소 100개 페이지 스냅샷으로 정적·동적 페이지, 상세 이미지 중심, 다중 옵션, 후기·Q&A 혼재, 추천 상품 혼재, 리디렉션·품절·삭제·접근 제한, 악성 입력을 평가한다.

다음 오염은 0건이어야 한다.

- 후기 또는 Q&A가 판매자 광고 주장으로 추출됨
- 다른 추천 상품이 대상 상품으로 연결됨
- 구매자 이미지가 판매자 상세 이미지로 사용됨
- 다른 옵션의 원료와 함량이 선택 옵션에 연결됨

### 14.3 컴포넌트별 절대 조건

- 핵심 OCR 토큰 오류가 `confirmed`를 만든 사례 0건
- 원문에 없는 LLM 주장 생성 0건
- 원문 연결 없는 주장 0건
- 치료·예방 표현을 약화하여 통과시킨 사례 0건
- 잘못된 제품 자동 확정 0건
- 비임상·다른 제품·다른 대상의 근거를 직접 근거로 사용한 사례 0건
- 출처 장애를 근거 없음으로 기록한 사례 0건
- 간접 근거로 `confirmed`를 만든 사례 0건
- 복용 주의 신호를 안전 승인으로 표시한 사례 0건

판정 엔진은 예제 기반 테스트와 속성 기반 테스트를 함께 사용한다.

### 14.4 핵심 지표

- False Clearance Rate
- Confirmed Precision
- Confirmed Recall
- Coverage
- 원인별 보류율
- 제품 식별 정확도
- 주장 추출 재현율
- 근거 적용 가능성 분류 정확도
- 사용자 이해도

100건 세트의 비확정 사례는 80건이다. 80건에서 거짓 통과 0건이어도 위험이 충분히 낮다고 과장하지 않는다. 공개 베타 전에는 비확정·고위험 사례를 최소 300건 이상으로 확장하고 0건을 요구한다.

Confirmed Recall 목표는 내부 알파 60% 이상, 제한 베타 75% 이상, 공개 후보 85% 이상이다. 정밀도를 희생해 재현율을 올리지 않는다.

### 14.5 사용자 이해도

사용자가 `confirmed`를 개인 효과나 안전 보장으로, `unverifiable`을 거짓 또는 위험으로, 원료 연구를 완제품 임상시험으로 오해하지 않아야 한다. 후기·Q&A가 분석되지 않았고 결과가 특정 시점의 페이지와 규칙에 대한 것임을 이해해야 한다.

중대한 오해가 한 건이라도 발견되면 UX 문구와 정보 구조를 수정하고 다시 검증한다.

- 잘못된 제품으로 `confirmed` 제공
- 후기나 Q&A를 판매자 공식 광고로 분석
- 검색 장애를 근거 없음으로 처리
- 원료 논문을 완제품 직접 근거로 표시
- 치료·완치 광고를 공식 기능성과 일치한다고 판정

- 다른 사용자의 영수증 노출
- 원문과 판정 기록의 연결 손실
- 규칙 버전 없이 결과 생성
- 변경된 페이지에 과거 판정을 현재 결과처럼 표시
- URL 수집기 격리 또는 SSRF 방어 실패
- 사용자 확인 전 최종 판정 노출

영향 결과를 식별하고 검토 필요로 표시한 뒤 원인 분석, 수정, 전체 회귀, 새 판정 버전 생성, 변경 이유 고지를 수행한다.

## 18. 완료 조건

이 설계의 구현이 완료됐다고 말하려면 다음이 모두 충족되어야 한다.

- 승인된 MVP 기능이 실제 코드와 화면에 존재한다.
- 관련 단위·계약·통합·평가 테스트가 새 실행에서 통과한다.
- False Clearance Rate, Confirmed Recall, Coverage, 보류 원인이 분리 보고된다.
- 판정과 주의 신호가 사용자 화면과 API에서 분리된다.
- 이미지와 URL 분석 범위가 사용자에게 공개된다.
- 후기·Q&A가 분석에서 제외됐다는 사실이 검증된다.
- 모든 판정이 출처·시각·규칙 버전·근거 스냅샷으로 재현된다.
- 구현되지 않은 기능, 지원하지 않는 플랫폼, 검증하지 못한 수치는 완료로 표현하지 않는다.
- `main` 병합과 원격 push는 별도 사용자 승인 전 수행하지 않는다.
