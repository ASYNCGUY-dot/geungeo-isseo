# 근거있어 확장 원료 추천 증거 게이트 설계

- 작성일: `2026-08-30 Asia/Seoul`
- 상태: 사용자 서면 명세 승인 완료 (`2026-08-30`)
- 보완 결정: 원료 귀속 문구가 다른 영양성분과 중복되는 규칙은
  `require_explicit_target_wording=true`로 차단 (`2026-08-31` 사용자 승인)
- 대상 브랜치: `phase-0-c003-data-gate`
- 선행 계약: `c003-product-review-v2`
- 대상 비교군: 밀크씨슬, 비타민 D, 홍삼, 코엔자임 Q10, 마그네슘

## 1. 결정

현재 C003 제품 검토 v2의 차단 상수를 임의로 해제하지 않는다. v2는 제품 매핑과
기능성 원문 사용 가능성을 검증하는 독립 감사 기록으로 보존하며, 완료 의미도 바꾸지
않는다.

확장 원료 추천은 다음 두 독립 증거 게이트의 pack 전체가 모두 `COMPLETE`일 때만
생성한다. `COMPLETE`는 정해진 수집·검토 계약이 끝났다는 뜻이며, 다섯 원료가 모두
추천 자격을 얻었다는 뜻은 아니다. 원료별 `ELIGIBLE`과 `INSUFFICIENT`는 별도로
보존한다.

1. **기능성 역할 게이트**: 원료명이 원재료에 존재하는 것과 해당 원료가 제품의 실제
   기능성 역할을 하는 것을 구분한다.
2. **공식 광고 근거 게이트**: 현재 시행 중인 공식 규정과 원료에 직접 연결되는 공식
   부당광고 자료를 재현 가능한 코퍼스로 만든다.

두 게이트를 통과해도 결과는 `READY_FOR_HUMAN_APPROVAL`인 추천안이다. 현재 수강
프로젝트에서는 사용자가 추천 근거영수증을 확인하고 승인해야 최종 선정된다. 실제 출시
정책에서는 제품 책임자와 건강기능 전문가, 식품 표시광고 전문가의 공동 승인을 요구한다.

기존 제품 MVP 설계대로 확장 원료는 두 개를 선정한다.

- 데이터와 결정 규칙이 비교적 명확한 원료 한 개
- 공식 광고 위험 신호와 서비스 가치가 높은 원료 한 개

추천과 최종 선정은 서로 다른 불변 산출물로 기록한다. 최종 승인 기록은 추천 산출물의
SHA-256을 참조하며, 추천 내용을 나중에 변경하면 기존 승인은 자동으로 무효가 된다.

## 2. 현재 확인된 출발점

2026-08-30에 실제 v2 pack을 다시 검증한 결과는 다음과 같다.

- 상태: `COMPLETE`
- 유효 사람 라벨: `100 / 100`
- 미완료 라벨: `0 / 100`
- 전체 매핑: `correct=99`, `incorrect=1`, `uncertain=0`
- 결정 가능 매핑 정밀도: `0.99`
- 전체 95% Wilson 구간: `0.9455138038` ~ `0.9982325679`
- 기능성 원문 사용 가능: `100 / 100`
- 광고 근거: `NOT_MEASURED`
- 확장 원료 추천: `BLOCKED`
- 최종 선정: `false`
- 라벨 파일 SHA-256:
  `A00B3C1A038DBFD06484A89A6C1B41AAA63837D3BD87FAC29E2AF5DF0E011CC1`

홍삼의 한 건은 `홍삼향분말`과 같은 별칭 충돌에 의한 거짓 양성이다. 이 오류는
기능성 역할 게이트에서 정상 표본으로 재해석하지 않고 `excluded_mapping_error`로
상속한다.

`function_text_status=usable`은 공식 기능성 원문이 후속 규칙 입력으로 사용 가능하다는
뜻이다. 그 원문이 현재 배정된 원료의 기능을 직접 설명한다는 뜻은 아니다. 예를 들어
원재료명에 스테아린산 마그네슘이 있더라도 공식 기능성 원문과 연결되지 않으면 해당
제품을 기능성 마그네슘 제품으로 확정할 수 없다.

현재 `ReviewValidationResult`가 광고 근거 `NOT_MEASURED`, 추천 `BLOCKED`, 최종 선정
`false`를 고정하는 것은 이 경계를 보존하기 위한 의도된 동작이다.

## 3. 공식 근거의 현재 기준

설계 작성일에 확인한 현재 시행 기준은 국가법령정보센터의
[`식품등의 부당한 표시 또는 광고의 내용 기준` 제2025-79호](https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000269428&chrClsCd=010201)다.
해당 고시는 2025-12-04 시행으로 표시되어 있다. 이후 행정예고나 개정안은 실제 시행이
확인되기 전까지 활성 규칙으로 사용할 수 없다.

식약처는 2026-04-30 건강기능식품 온라인 부당광고 점검 결과를 공식 보도자료로
공개했으며, 온라인 부당광고 점검과 조치가 실제 공식 자료로 존재함을 확인할 수 있다.
다만 게시물의 합계 수치만으로 개별 원료 사례를 복제하거나 추정할 수는 없다.

- [2026년 식약처 건강기능식품 온라인 부당광고 점검 결과](https://www.mfds.go.kr/brd/m_99/view.do?seq=49936)
- [2024년 식약처 온라인 부당광고 89건 적발·조치 자료](https://www.mfds.go.kr/brd/m_99/view.do?seq=48237)
- [식품 등의 표시ㆍ광고에 관한 법률](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=251773)

공식 자료의 존재와 원료별 증거의 충분성은 별개다. 첨부자료가 개별 광고, 원료 또는
제품, 위반 유형을 직접 연결하지 않으면 그 문서는 `aggregate_context`로만 보존하고
원료별 직접 사례 수에는 포함하지 않는다.

## 4. 검토한 접근 방식

### 4.1 차단 상수만 변경

v2의 `NOT_MEASURED`와 `BLOCKED`를 `MEASURED`와 `READY`로 바꾸는 방식이다.

- 장점: 구현이 가장 빠르다.
- 문제: 광고 근거가 없는데 있는 것처럼 표시하며, 기존 테스트와 감사 계약을 거짓으로
  만든다.
- 결정: **기각**한다.

### 4.2 기존 1~5점 점수표 재사용

사람이 광고 위험, 기능성 다양성, 구현 가능성을 1~5점으로 입력하고 평균 점수로
선정하는 방식이다.

- 장점: 다섯 후보를 쉽게 순위화할 수 있다.
- 문제: C003 표본에는 광고 원문이 없고, 점수의 근거·집계 규칙·오차 범위가 없다.
  서로 다른 성격의 불확실성을 평균하면 부족한 증거가 중간 점수로 위장된다.
- 결정: **기각**한다. 보존된 v1 점수 코드는 새 추천 흐름에서 호출하지 않는다.

### 4.3 단계형 독립 증거 게이트

기능성 역할과 광고 근거를 별도 계약으로 측정하고, 두 검증 결과만 결정론적 추천기에
전달하는 방식이다.

- 장점: 누락과 불확실성을 독립 상태로 보존하며, 어떤 증거 때문에 추천이 막혔는지
  설명할 수 있다. 규칙 변경과 재검증도 개별 게이트 단위로 가능하다.
- 비용: 공식 자료 수집과 사람 검토가 추가되고, 증거가 부족하면 추천이 계속 막힐 수
  있다.
- 결정: **채택**한다. 정확성과 감사 가능성을 속도보다 우선한다.

## 5. 전체 범위와 구현 분해

이 설계는 세 개의 순차 하위 작업으로 나눈다.

1. `A — functional-role-gate`: 기능성 역할 규칙, 검토 pack, 검증기와 정확도 측정
2. `B — official-ad-evidence-gate`: 공식 규정 레지스트리, 공식 사례 코퍼스와 검증기
3. `C — extension-recommendation-finalization`: 두 요약의 결합, 추천 근거영수증과 승인
   원장

각 하위 작업은 앞 단계의 버전과 해시를 입력으로 받는다. 한 번의 구현 계획으로 세
영역을 동시에 수정하지 않는다. 첫 구현 계획은 `A`만 대상으로 하며, `A`가 검증된 뒤
`B`, 그 뒤 `C`를 별도 계획으로 진행한다.

### 포함

- 기존 다섯 비교군과 C003 제품정보
- 기존 v2의 100개 복합 키와 사람 검토 결과 보존
- 목표 원료의 제품 내 기능성 역할 구분
- 현재 시행 규정의 버전·시행일·출처 보존
- 식약처 등 공식 출처의 광고 사례 수집과 사람 확인
- 근거 충분성, 규칙 적용 범위, 불확실성과 오차 구간
- 두 역할의 확장 원료 추천안
- 프로젝트용 사용자 승인과 출시용 전문가 공동 승인 정책

### 제외

- v2 라벨 또는 역사적 v1 pack 덮어쓰기
- 화장품, 의약품, 일반식품으로 범위 확장
- 판매량·노출량 분모 없는 시장 위반률 추정
- 법적 확정, 무혐의, 심의 통과 보증
- 약사·영양사·표시광고 전문가의 최종 책임을 AI로 대체
- OCR, URL crawler, RAG, LangGraph, FastAPI, React 구현
- 학습용 가상 사례를 실제 행정사례로 사용하는 행위

## 6. 권위 출처 계약

### 6.1 출처 우선순위

1. 국가법령정보센터의 현재 시행 법률·시행령·시행규칙·행정규칙
2. 식품의약품안전처의 고시전문·제개정문·공식 공고
3. 식품의약품안전처의 공식 보도자료와 첨부 원문
4. 식품안전나라의 공식 제품·업체·행정처분 정보

협회, 언론, 블로그, 쇼핑몰, 검색 결과 요약은 공식 원문 탐색용 후보로는 사용할 수
있지만 활성 규칙이나 직접 행정사례의 정본이 될 수 없다.

### 6.2 규칙 시점

- 모든 규칙은 `source_id`, `source_url`, `promulgated_at`, `effective_from`,
  `effective_to`, `retrieved_at`, `content_sha256`, `rule_version`을 보존한다.
- 행정예고·개정안은 `proposed`로 저장하며 활성 규칙 집합에서 제외한다.
- 사례 발생일의 규칙과 추천 생성일의 현재 규칙을 모두 연결한다.
- 추천 생성 시 `verified_current_at`이 7일을 초과한 규칙 스냅샷은
  `STALE_RULES`로 차단한다. 7일은 프로젝트 운영 정책이며 법적 유효기간을 뜻하지
  않는다.
- 공식 문서가 수정되면 URL이 같아도 SHA-256 변경을 새 버전으로 처리한다.

### 6.3 사례 단위

- 공식 첨부에 서로 구분되는 광고·제품·업체 행이 있을 때만 각각의 사례로 센다.
- “47건 적발”처럼 합계만 있는 자료는 하나의 `aggregate_context` 문서다.
- 하나의 광고가 여러 게시물 또는 여러 보도자료에 반복되어도 claim fingerprint와
  공식 식별자로 중복 제거한다.
- 원료 연결이 직접 확인되지 않으면 특정 비교군에 배정하지 않는다.
- 원문이나 직접 인용 위치가 없으면 위반 문구를 생성하거나 복원하지 않는다.

## 7. A — 기능성 역할 게이트

### 7.1 목적

현재 alias 규칙이 “원재료에 목표 표현이 존재함”을 찾는 단계에서 더 나아가, 목표
원료가 해당 제품의 공식 기능성 역할을 한다는 긍정 판정을 얼마나 정확하게 생성하는지
측정한다.

### 7.2 입력

- `data/c003-products.jsonl`의 현재 SHA-256
- `build/extension-review-v2/manifest.json`
- `build/extension-review-v2/samples.csv`
- `build/extension-review-v2/product_review_labels.csv`
- 현재 시행 중인 건강기능식품 원료·기능성 규칙 레지스트리

v2가 `COMPLETE`가 아니거나 입력 해시가 바뀌면 pack을 만들지 않는다.

건강기능식품 원료·기능성 규칙 레코드는 최소 `group`, `canonical_ingredient`,
`accepted_functional_forms`, `recognized_function_texts`,
`require_explicit_target_wording`, `source_id`, `source_url`, `effective_from`,
`effective_to`, `source_locator`, `content_sha256`, `rule_version`을 가진다. 규칙은
원재료 문자열과 기능성 문자열을 독립적으로 확인한 뒤 두 근거가 현재 제품에 함께
적용될 때만 긍정 판정을 허용한다. 공식 기능 문구가 다른 원료의 기능 문구와 중복되어
원료 귀속을 단독 식별할 수 없는 규칙은 `require_explicit_target_wording=true`로 두고,
기능성 문자열에 목표 원료명이 직접 연결될 때만 긍정 판정을 허용한다.

### 7.3 로컬 pack

`build/functional-role-review-v1/`에 정확히 다음 네 파일을 둔다.

1. `README.md`
2. `manifest.json`
3. `samples.csv`
4. `functional_role_labels.csv`

`samples.csv`의 최초 100행은 v2 표본과 복합 키·제품 원문이 같아야 한다. 이후 정밀도
확인을 위한 추가 표본은 별도 `audit_round`를 갖고 결정적 표본 추출 규칙으로만 추가한다.
`group + report_no`는 pack 전체에서 유일해야 하며, 기존 100건과 겹친 긍정 표본은
중복 행을 만들지 않고 기존 행에 해당 audit round를 기록한다. pack 전체는 계속 Git에서
제외하고, 집계와 해시만 추적 문서에 기록한다.

### 7.4 자동 규칙 출력

규칙 엔진의 제품별 출력은 다음 세 상태로 제한한다.

| 상태 | 의미 |
|---|---|
| `functional_confirmed` | 목표 원료의 공식 기능성 역할과 적용 기능이 명시적 규칙으로 연결됨 |
| `present_nonfunctional` | 공식 원문이 목표 표현의 비기능성 역할을 명시적으로 지지함 |
| `unverifiable` | 역할을 확정할 필드·규칙·연결 근거가 부족하거나 충돌함 |

다음 경계를 지킨다.

- 원재료 alias 일치만으로 `functional_confirmed`를 만들지 않는다.
- 목표 기능 문구가 없다는 사실만으로 `present_nonfunctional`을 만들지 않는다.
- 조합제품에서 원료와 기능의 연결이 명시되지 않으면 `unverifiable`이다.
- `require_explicit_target_wording=true`인 규칙은 원료형과 기능 문구가 모두 있어도
  기능성 문자열에 목표 원료명이 직접 연결되지 않으면 `unverifiable`이다.
- `present_nonfunctional`은 제조용·첨가용 등 비기능 역할을 공식 원문이 직접 지지할
  때만 사용한다.
- LLM은 증거 후보와 원문 위치를 제시할 수 있지만 이 세 상태를 확정하지 않는다.

### 7.5 사람 기준 라벨

사람 라벨은 다음 네 상태를 사용한다.

| 상태 | 의미 |
|---|---|
| `functional_confirmed` | 목표 원료의 기능성 역할이 공식 원문과 규칙으로 확인됨 |
| `present_nonfunctional` | 목표 표현이 있지만 비기능성 역할임이 확인됨 |
| `uncertain` | 전문가 없이 역할을 참·거짓으로 결정할 수 없음 |
| `excluded_mapping_error` | v2에서 확인된 원료군 오매핑을 상속함 |

최소 열은 `group`, `report_no`, `audit_round`, `machine_verdict`,
`human_verdict`, `reason_code`, `evidence_field`, `evidence_excerpt`,
`rule_version`, `review_note`, `reviewer`, `reviewed_at_iso8601`이다.

`evidence_excerpt`는 원문 밖의 의미를 보충할 수 없고, spreadsheet formula prefix와
비밀정보 패턴을 거부한다. `uncertain`, `present_nonfunctional`,
`excluded_mapping_error`에는 호환되는 이유 코드가 필수다.

### 7.6 정확도 지표와 적응형 표본

가장 중요한 지표는 `functional_confirmed` 긍정 판정의 거짓 양성이다.

- `positive_precision = true_functional_confirmed / machine_functional_confirmed`
- `false_confirmation_count`
- `unresolved_positive_count`
- `positive_precision_wilson_95`
- 전체 machine/human confusion matrix
- `decidable_agreement_rate`
- `false_exclusion_count`
- `avoidable_unverifiable_count`
- `decision_coverage`
- `unverifiable_rate`
- `human_uncertainty_rate`
- 그룹별 `addressable_product_count`

기존 20건은 각 그룹의 오류 유형 탐색에 재사용한다. 긍정 정밀도 검증은 다섯 그룹
모두에서 전체 `machine_functional_confirmed` 풀을 대상으로 동일한 결정적 무작위
추출 규칙을 사용한다. 추천 결과를 본 뒤 유리한 후보만 추가 검토하거나 사람이 보기
쉬운 사례만 고르는 표본은 금지한다.

사람이 `functional_confirmed`로 확인한 기계 긍정만 정답 분자에 들어간다. 기계가
`functional_confirmed`인데 사람이 `present_nonfunctional`로 확인하면 거짓 양성이고,
사람이 `uncertain`이면 `unresolved_positive`다. 둘 다 긍정 정답으로 계산하지 않는다.

기계의 `present_nonfunctional`이 사람의 `functional_confirmed`와 충돌하면
`false_exclusion`이다. 기계의 확정 상태가 사람의 `uncertain`과 충돌하면
`overconfident_decision`으로 규칙 수정을 요구한다. 반대로 기계가 `unverifiable`이고
사람은 결정할 수 있었던 행은 긍정 오판은 아니지만 `avoidable_unverifiable`로 기록해
명확성 후보의 `decision_coverage`를 낮춘다.

기존 무작위 20건 중 `excluded_mapping_error`가 나오면 그룹 내 같은 seed 계열의 다음
고유 제품으로 보충해 기능성 역할의 일반 감사 분모를 다시 20건으로 맞춘다. 보충 전
오매핑 행은 삭제하지 않고 제외 이유와 함께 보존한다.

그룹이 `ROLE_ELIGIBLE`이 되려면 다음을 모두 만족해야 한다.

1. 모든 감사 행이 유효하고 원본·규칙·v2 해시가 일치한다.
2. 그룹별 일반 감사 20건에서 기계 확정과 사람 확정의 충돌이 `0`이다.
3. 관측된 `false_confirmation_count`와 `false_exclusion_count`가 모두 `0`이다.
4. `unresolved_positive_count`와 `overconfident_decision_count`가 모두 `0`이다.
5. `positive_precision_wilson_95.lower >= 0.90`이다.
6. 긍정 판정 표본이 최소 35건이다. 35건 모두 정답이면 현재 사용 중인 양측 95%
   Wilson 공식에서 하한이 약 0.90이 된다.
7. `uncertain`을 오답과 합쳐 숨기지 않고 별도 비율로 공개한다.
8. 전체 풀의 `addressable_product_count`가 `0`보다 크다.

긍정 풀에 고유 제품이 35건 미만이면 해당 그룹은 `ROLE_INSUFFICIENT`다. 감사에서
거짓 양성 또는 해결되지 않은 긍정이 발견되어도 같은 상태다. 원인을 수정하려면 새 규칙
버전을 만들고 pack을 처음부터 재생성해야 한다. 수정 전 표본은 회귀 fixture로는
보존하지만 새 규칙의 성공 표본으로 재사용하지 않는다.

이 기준은 절대 무오류를 보장하지 않는다. 관측된 거짓 양성 0건과 표본 기반 정밀도
하한을 동시에 요구해 긍정 오판 위험을 보수적으로 제한하는 프로젝트 정책이다.

### 7.7 pack 상태와 원료 자격 상태

pack 전체는 다음 상태를 사용한다.

| pack 상태 | 조건 |
|---|---|
| `PENDING` | 구조는 맞지만 사람 라벨이 미완료 |
| `INVALID` | 해시·키·열·enum·시간·규칙 연결이 손상됨 |
| `COMPLETE` | 다섯 그룹의 정해진 감사와 집계가 모두 끝남 |

`COMPLETE` summary 안에서 각 원료는 다음 자격 상태 중 하나를 가진다.

| 원료 자격 상태 | 조건 |
|---|---|
| `ROLE_INSUFFICIENT` | 검토는 완료됐지만 긍정 풀 또는 정확도 정책을 충족하지 못함 |
| `ROLE_ELIGIBLE` | 모든 무결성·긍정 정밀도 조건을 충족함 |

## 8. B — 공식 광고 근거 게이트

### 8.1 목적

각 비교군에 적용 가능한 현재 규칙과 공식 부당광고 사례를 분리해 측정한다. 이 단계는
시장 전체의 위반 확률을 추정하지 않는다.

### 8.2 코퍼스 구성

추적 가능한 규칙 정의와 집계만 저장소에 둔다. 원본 PDF·HWP·HWPX 및 추출 작업물은
`build/official-ad-evidence-v1/`에 보존하고 Git에서 제외한다.

각 규칙 레코드는 최소 다음 필드를 가진다.

- `rule_id`, `rule_version`, `authority`, `source_id`, `source_url`
- `promulgated_at`, `effective_from`, `effective_to`, `status`
- `claim_family`, `applicability`, `source_locator`
- `retrieved_at`, `content_sha256`

각 사례 레코드는 최소 다음 필드를 가진다.

- `case_id`, `document_id`, `case_granularity`
- `official_source_id`, `official_source_url`, `published_at`
- `group`, `product_or_ingredient_text`, `claim_text`
- `claim_family`, `violation_basis`, `rule_version`
- `action_type`, `source_locator`, `retrieved_at`, `content_sha256`
- `attribution_status`, `reviewer`, `reviewed_at_iso8601`

### 8.3 수집 프로토콜

- 수집 기간은 `2021-01-01`부터 실행일 자정 KST까지로 고정한다.
- 검색 대상·검색어·페이지 범위·실행 시각을 manifest에 기록한다.
- 공식 게시물과 첨부파일을 모두 확인하되 검색 결과 요약만으로 사례를 만들지 않는다.
- OCR 또는 LLM 추출은 후보 행만 만들고, 사람이 공식 원문 위치와 원료 귀속을
  확인해야 유효 사례가 된다.
- 동일 광고의 재게시, 보도자료 재인용, URL 변형은 fingerprint로 중복 제거한다.
- 직접 원료 귀속이 없는 자료는 `aggregate_context`로만 보존한다.
- 공식 페이지가 사라지면 검증된 로컬 원본 해시가 있는 역사 자료로만 보존하고, 현재
  추천의 직접 근거 사용 여부는 별도 `source_availability`로 표시한다.

2021-01-01은 최근 약 5개 완전 연도와 현재 연도를 포함하기 위한 프로젝트 수집
정책이다. 광고 발생률의 통계적 대표성을 보장하는 기간으로 표현하지 않는다.

### 8.4 측정값

각 그룹에서 다음만 계산한다.

- 현재 적용 가능한 `claim_family_count`
- 직접 귀속 공식 사례 수 `direct_case_count`
- 서로 다른 공식 문서 수 `distinct_official_document_count`
- 서로 다른 위반 주장군 수 `distinct_case_claim_family_count`
- 직접 귀속 불가 `aggregate_context_count`
- 중복 제거 수와 제외 이유
- 최신 규칙 확인 시각과 코퍼스 종료일

판매량, 광고 노출량 또는 전체 광고 수가 없으므로 다음 표현은 만들지 않는다.

- 위반률
- 적발 확률
- 소비자가 속을 확률
- 시장 전체 과장광고 비율

### 8.5 고위험·고가치 후보의 최소 근거

`HIGH_RISK_SIGNAL_ELIGIBLE`은 다음 프로젝트 정책을 모두 만족해야 한다.

1. `ROLE_ELIGIBLE`이다.
2. 현재 규칙 레지스트리가 유효하고 7일 이내 재확인되었다.
3. 직접 귀속 공식 사례가 3건 이상이다.
4. 직접 사례가 최소 2개의 서로 다른 공식 문서 또는 공표일에 걸쳐 있다.
5. 직접 사례가 최소 2개의 서로 다른 위반 주장군을 포함한다.
6. 최소 하나의 사례가 질병 예방·치료 또는 의약품 오인과 같이 서비스가 우선 검증할
   소비자 위해 우려 주장군에 속한다. 이는 법정 처분 수위가 아니라 프로젝트의 검증
   우선순위다.

이 최소치는 위반률을 추정하기 위한 통계 기준이 아니다. 하나의 사건이나 하나의
보도자료에만 의존한 “고위험” 낙인을 피하기 위한 보수적 추천 자격 기준이다. 조건을
충족하는 그룹이 없으면 두 번째 자리를 억지로 채우지 않고
`AD_EVIDENCE_INSUFFICIENT`를 반환한다.

### 8.6 pack 상태와 원료 증거 상태

광고 근거 pack 전체는 다음 상태를 사용한다.

| pack 상태 | 조건 |
|---|---|
| `NOT_MEASURED` | 수집 프로토콜을 실행하지 않음 |
| `PENDING` | 원문 수집 또는 사람 확인이 미완료 |
| `INVALID` | 출처·해시·중복·규칙 연결 계약이 손상됨 |
| `COMPLETE` | 정해진 기간·검색·사람 확인과 다섯 그룹 집계가 모두 끝남 |

`COMPLETE` summary 안에서 각 원료는 다음 상태 중 하나를 가진다.

| 원료 증거 상태 | 조건 |
|---|---|
| `MEASURED_NO_DIRECT_CASE` | 정해진 검색을 완료했지만 직접 귀속 사례를 찾지 못함 |
| `AD_EVIDENCE_INSUFFICIENT` | 직접 근거는 있으나 고위험 후보 최소치를 충족하지 못함 |
| `AD_EVIDENCE_ELIGIBLE` | 규칙과 직접 사례의 무결성·최소 근거를 충족함 |

`MEASURED_NO_DIRECT_CASE`는 위험이 없다는 뜻이 아니다.

## 9. C — 추천과 최종 승인

### 9.1 입력 경계

추천기는 원본 CSV나 자유서술 점수를 읽지 않는다. 다음 검증 결과만 입력으로 받는다.

- 유효한 C003 제품 검토 v2 요약과 해시
- 그룹별 기능성 역할 게이트 요약과 규칙 버전
- 그룹별 공식 광고 근거 게이트 요약과 코퍼스 버전
- C003 전체 풀의 그룹별 완전성·주소 가능 제품 수

두 선행 pack 중 하나라도 `PENDING`, `INVALID`, `STALE_RULES`, `NOT_MEASURED`면 추천을
만들지 않는다. 두 pack이 `COMPLETE`여도 `ROLE_ELIGIBLE` 원료가 두 개 미만이거나,
명확성 원료를 제외한 뒤 `AD_EVIDENCE_ELIGIBLE` 원료가 하나도 없으면
`BLOCKED_EVIDENCE_INSUFFICIENT`다.

### 9.2 명확성 원료 선정

먼저 `ROLE_ELIGIBLE` 그룹만 남기고 다음 순서의 결정론적 비교를 사용한다.

1. 기능성 역할 규칙의 `decision_coverage`가 높은 그룹
2. 긍정 정밀도 Wilson 95% 하한이 높은 그룹
3. C003 여섯 필드 완전성이 높은 그룹
4. `addressable_product_count`가 큰 그룹
5. 완전 동률이면 고정된 `group` 코드 사전순

광고 직접 사례가 없더라도 공식 검색이 완료되어
`MEASURED_NO_DIRECT_CASE`로 구분된 그룹은 명확성 원료 후보가 될 수 있다. 다만 근거
영수증에 “직접 사례를 찾지 못했으며 위험 없음으로 해석할 수 없음”을 표시한다.

### 9.3 고위험·고가치 원료 선정

명확성 원료를 제외하고 `HIGH_RISK_SIGNAL_ELIGIBLE` 그룹만 남긴다. 다음 순서로
비교한다.

1. 서로 다른 직접 사례 위반 주장군 수
2. 서비스 우선 검증 주장군의 존재와 수
3. 기능성 역할 규칙의 `addressable_product_count`
4. 기능성 역할 규칙의 `decision_coverage`
5. 완전 동률이면 고정된 `group` 코드 사전순

원시 적발 건수는 첫 번째 정렬키로 사용하지 않는다. 하나의 집중점검 규모가 순위를
왜곡할 수 있기 때문이다. 홍삼은 고위험·고가치 비교군으로 계속 유지하지만 증거 없이
자동 선정하지 않는다.

### 9.4 추천 근거영수증

추천 결과는 최소 다음을 보존한다.

- `recommendation_contract_version`
- 명확성 원료와 고위험·고가치 원료
- 각 후보와 탈락 후보의 자격 상태
- 사용한 세 입력 요약의 SHA-256
- 규칙·코퍼스·원료 매핑 버전
- 비교에 사용한 원시 지표와 순서
- 제외 이유와 미측정·불충분 상태
- 생성 시각과 코퍼스 종료일
- `status=READY_FOR_HUMAN_APPROVAL`
- `finalized=false`

LLM이 작성한 설명은 선택 결과를 바꿀 수 없다. 설명은 결정론적 지표와 출처를
문장으로 풀어쓰는 역할만 한다.

### 9.5 승인 원장

추천 객체를 수정해 `finalized=true`로 바꾸지 않는다. 별도 불변 승인 레코드가 추천
SHA-256을 참조하며 최종 상태는 둘을 함께 검증해 계산한다.

프로젝트 정책 `project-demo-v1`은 다음을 요구한다.

- 사용자 승인자 식별자
- 추천 SHA-256
- 선택된 두 역할과 원료
- 승인 또는 반려
- 승인 시각과 짧은 근거

출시 정책 `production-v1`은 다음을 추가로 요구한다.

- 제품 책임자 승인
- 약사 또는 영양사 등 건강기능 전문가 승인
- 식품 표시광고 실무 전문가 승인
- 각 전문가의 검토 범위와 자격 확인 기록
- 미해결 전문가 이견 `0건`

같은 사람이 여러 역할을 맡는 운영은 자격과 독립성 정책을 별도 승인하기 전까지
허용하지 않는다. 이 승인 구조도 공식 심의 통과나 법적 적합성 보증을 뜻하지 않는다.

### 9.6 추천 상태

| 상태 | 의미 |
|---|---|
| `BLOCKED_INPUT_PENDING` | 선행 검토가 미완료 |
| `BLOCKED_INPUT_INVALID` | 입력 또는 해시 계약 손상 |
| `BLOCKED_STALE_RULES` | 현재 규칙 확인 시각 만료 |
| `BLOCKED_EVIDENCE_INSUFFICIENT` | 두 역할 중 하나 이상을 채울 근거 부족 |
| `READY_FOR_HUMAN_APPROVAL` | 두 후보와 근거영수증 생성 완료 |
| `FINALIZED` | 현재 운영 정책에 맞는 별도 승인 원장이 유효 |

이 상태명은 내부 감사용이다. 사용자 화면에서는 미완료·부족·재확인 필요를 자연어로
설명하고 내부 enum을 그대로 노출하지 않는다.

## 10. 오류·불확실성 처리

- 원료·제품·사례 귀속 충돌은 낮은 점수로 변환하지 않고 차단한다.
- 공식 출처가 아닌 가상 사례는 `INVALID_SOURCE`다.
- 공식 합계와 개별 사례 수가 맞지 않아도 누락 사례를 생성해 맞추지 않는다.
- 규칙의 시행일을 사례일에 적용할 수 없으면 `RULE_NOT_APPLICABLE`이다.
- 현재 규칙과 과거 처분 규칙이 달라지면 둘을 각각 보존한다.
- 문서 원문이 깨지거나 OCR만 존재하면 사람이 원문을 확인하기 전까지 `PENDING`이다.
- 원료 직접 귀속이 불가능하면 `aggregate_context` 또는 `uncertain`이다.
- 두 추천 역할에 같은 원료를 중복 배정하지 않는다.
- 조건을 충족한 후보가 없으면 빈 자리를 그대로 두고 차단 사유를 출력한다.
- 외부 출처 장애를 “위반 사례 없음”으로 변환하지 않는다.

## 11. 보안과 감사 추적

- API 키, 로그인 쿠키, 사용자 건강정보를 pack이나 추적 문서에 저장하지 않는다.
- 공식 원본 다운로드와 OCR 중간 산출물은 정확한 ignored 경로에 둔다.
- 추적 파일에는 redacted fixture, 계약, 집계, 버전과 해시만 둔다.
- CSV 자유 입력은 `=`, `+`, `-`, `@`, tab, carriage return 시작을 거부한다.
- URL은 HTTP(S)와 공식 허용 도메인을 모두 만족해야 한다.
- source locator는 페이지·표·행 또는 문단을 가리켜야 하며 원문 전체 복제를 피한다.
- 생성기·검증기·추천기·승인기는 모두 오프라인 fixture로 재현 가능해야 한다.

## 12. 테스트 전략

### 12.1 기능성 역할 게이트

1. v2가 `COMPLETE`가 아니면 pack 생성을 거부한다.
2. v2 label·sample·export 해시 변경을 거부한다.
3. 원재료 alias만 일치하고 목표 기능 연결이 없으면 긍정 판정을 만들지 않는다.
4. 명시적 대상 연결 정책이 켜진 마그네슘 규칙은 칼슘과 중복되는 기능 문구만으로
   기능성 마그네슘을 확정하지 않는다.
5. 스테아린산 마그네슘 표현만 있는 합성 fixture는 기능성 마그네슘으로 확정하지 않는다.
6. 홍삼향분말 alias 충돌은 `excluded_mapping_error`를 상속한다.
7. 조합제품의 원료·기능 연결이 불명확하면 `unverifiable` 또는 사람 `uncertain`이다.
8. 긍정 표본 35/35의 Wilson 하한과 독립 계산이 일치한다.
9. 관측 거짓 양성 1건이면 `ROLE_ELIGIBLE`이 될 수 없다.
10. 해결되지 않은 기계 긍정 1건도 `ROLE_ELIGIBLE`이 될 수 없다.
11. 거짓 제외와 과신한 비기능성 판정을 각각 거부한다.
12. v2 오매핑 행은 보존하면서 결정적으로 보충해 일반 감사 20건을 유지한다.
13. 모든 그룹이 같은 표본 규칙을 사용하고 추천 후 선택적 재표본을 금지한다.
14. 표본 선택은 입력 순서와 무관하고 같은 seed·규칙 버전에서 동일하다.
15. 잘못된 enum·이유·원문 위치·시각·formula 입력을 거부한다.

### 12.2 공식 광고 근거 게이트

1. 행정예고와 시행 전 규칙은 활성 규칙으로 사용할 수 없다.
2. 현재 시행 규칙의 URL·시행일·해시·버전을 모두 요구한다.
3. 공식 도메인이 아닌 사례를 직접 근거로 거부한다.
4. “47건 적발” 합계를 47개 사례로 확장하는 입력을 거부한다.
5. 같은 광고의 URL 변형·재게시·재인용을 중복 제거한다.
6. 원료 직접 귀속이 없으면 그룹별 직접 사례 수에 포함하지 않는다.
7. 판매량·노출량 분모 없이 위반률 필드를 만들 수 없다.
8. 규칙 확인 시각이 7일을 초과하면 `STALE_RULES`다.
9. 직접 사례 3건, 문서·공표일 2개, 주장군 2개 조건을 각각 검증한다.
10. 원문 위치나 사람 확인이 빠지면 `PENDING`이다.

### 12.3 추천과 승인

1. 선행 게이트 하나라도 미완료·손상·만료이면 추천 객체가 생성되지 않는다.
2. 동일 입력에서 추천과 근거영수증 JSON이 바이트 단위로 결정적이다.
3. 기존 자유서술 1~5점은 새 추천 입력으로 거부한다.
4. 명확성·고위험 원료가 중복되지 않는다.
5. 적격 고위험 후보가 없으면 임의 대체 후보를 선택하지 않는다.
6. 동률 해소 순서가 문서 계약과 일치한다.
7. 추천 결과는 항상 `finalized=false`다.
8. 승인 원장의 추천 SHA-256이 다르면 `FINALIZED`가 될 수 없다.
9. 프로젝트 승인과 출시 전문가 공동 승인 정책을 분리한다.
10. 내부 상태가 사용자 화면 문구로 직접 노출되지 않는 계약을 검증한다.

각 하위 작업은 해당 단위 테스트뿐 아니라 전체 pytest, coverage, Ruff,
`git diff --check`, 비밀정보·금지어 검사를 통과해야 한다.

## 13. 완료 기준

이 전체 설계의 구현이 완료됐다고 말하려면 다음이 모두 직접 검증되어야 한다.

- v2 pack과 역사적 v1 pack이 변경되지 않음
- 기능성 역할 규칙과 사람 감사 결과가 그룹별 상태·오차 구간을 생성함
- 확장 후보가 될 그룹의 긍정 판정에서 관측 거짓 양성 0건과 Wilson 하한 0.90 이상을
  확인함
- 공식 규정 레지스트리와 사례 코퍼스가 출처·시점·해시·원문 위치를 보존함
- 집계형 문서와 직접 원료 사례가 분리됨
- 시장 분모 없는 위반률이 어디에도 생성되지 않음
- 두 추천 역할을 결정론적으로 선택하거나 근거 부족으로 차단함
- 추천 객체와 승인 원장이 분리되어 있음
- 프로젝트 사용자 승인 없이는 `FINALIZED`가 되지 않음
- 출시 정책 fixture에서는 세 승인 역할과 무이견 조건을 충족해야 함
- 모든 검증 명령과 실제 결과가 evidence·handoff 문서에 기록됨
- main merge, 원격 push, PR 생성, worktree 삭제는 별도 사용자 승인 전까지 수행되지 않음
